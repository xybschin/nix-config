# CONTEXT.md Integration Guide

This skill integrates with the project's `CONTEXT.md` file following the `grill-with-docs` pattern. This guide explains how to check, create, and update CONTEXT.md during the architecture overview process.

## File Structure

Most projects follow one of two patterns:

### Single Context (most projects)

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-*.md
│       └── 0002-*.md
└── src/
```

### Multiple Contexts (monorepos)

```
/
├── CONTEXT-MAP.md (points to where each context lives)
├── docs/
│   └── adr/ (system-wide decisions)
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

## Before Writing the Report

### 1. Check for Existing CONTEXT.md

**Single context:** Look for `/CONTEXT.md` at the repo root.

**Multiple contexts:** Look for `/CONTEXT-MAP.md` first. If it exists, read it to locate each context's CONTEXT.md file. For this report, focus on one context (usually the largest or most complex). Ask the user which context to analyze if unclear.

### 2. Read Existing Documentation

If CONTEXT.md exists:
- Read the **Overview** section — understand how the project describes itself
- Read the **Glossary** — note the domain vocabulary already established
- Read the **Architecture** section — understand documented architectural decisions
- Cross-reference discovered architecture against documented architecture
  - If there's a gap, note it (maybe the code has diverged from docs)
  - If terminology differs (code uses "Order", docs say "OrderEntity"), flag it

### 3. Establish Vocabulary

From the codebase exploration:
- Identify core domain concepts (Order, Inventory, Payment, etc.)
- Note how the codebase names these concepts (class names, module names, file paths)
- Check if the codebase terminology matches CONTEXT.md
- If CONTEXT.md doesn't exist, the code's vocabulary becomes the foundation

## Creating CONTEXT.md

If the project has no CONTEXT.md, create one **after** analyzing the codebase. Use the discovered vocabulary and structure.

### Template

```markdown
# CONTEXT.md — {{System Name}}

## Overview

{{Describe what this system does in 2-3 sentences. Who uses it? What problems does it solve?}}

Example: "This is the Order Management System. It manages the complete order lifecycle from customer intake through fulfillment and delivery. Used by customer-facing web app and internal fulfillment team."

## Core Domains

{{List main business concepts and their relationships. These become the modules in your overview.}}

Example:
- **Order** — a customer's request for goods or services
- **Inventory** — available stock across warehouses
- **Fulfillment** — process of picking, packing, and shipping orders

## Glossary

{{Domain vocabulary extracted from the codebase. Each term grounded in business logic and code location.}}

**Format:**
- **{{Term}}** — {{plain English definition}}
  - Used in: `src/path/to/code.ts`, `src/models/Order.ts`

Example:
- **Order** — a customer's request for goods. Orders progress through states: pending → confirmed → fulfilled → delivered.
  - Used in: `src/models/Order.ts`, `src/modules/order/`

- **Fulfillment** — process of picking, packing, and shipping an order.
  - Used in: `src/modules/fulfillment/`

- **SKU** (Stock Keeping Unit) — unique identifier for a product variant.
  - Used in: `src/models/Inventory.ts`

## Architecture

{{High-level architectural decisions and constraints.}}

Example:
- Layered architecture with clear separation: API layer (controllers) → Service layer (business logic) → Data layer (repositories)
- Repository pattern for data access abstraction
- Adapter pattern for external integrations (Stripe, FedEx)
- Dependency injection for loose coupling and testability
- State machine for order lifecycle management

## Integration Points

{{External systems and APIs.}}

Example:
- **Stripe API** — payment processing
- **PostgreSQL** — primary data store
- **Redis** — caching layer
- **FedEx API** — shipping label generation
- **Inventory System** — real-time stock sync (HTTP API)

## Related Documentation

- Architecture report: `docs/architecture-overview-YYYY-MM-DD.md` (generated by codebase-architecture-overview skill)
- Architecture decision records: `docs/adr/`
```

## Updating Existing CONTEXT.md

If CONTEXT.md already exists:

1. **Compare terminology** — does the codebase use the same terms as CONTEXT.md?
   - If yes, use CONTEXT.md's terminology in the report
   - If no, flag the discrepancy (inconsistency is worth noting)

2. **Enrich the Glossary** — add terms discovered during analysis that aren't in CONTEXT.md yet
   - Only add terms grounded in code and business logic
   - Link to code locations

3. **Update Architecture section** — if the actual architecture has evolved beyond what's documented
   - Note what's changed
   - Don't invent architectural patterns; only document what you observe in the code

4. **Don't rewrite** — respect the existing structure and ownership
   - If CONTEXT.md was written by domain experts, preserve their phrasing
   - Merge your findings without overwriting

## Example Integration

**Initial CONTEXT.md:**
```markdown
# CONTEXT.md

## Overview
Order management system.

## Glossary
- **Order** — customer request for goods

## Architecture
Layered architecture.
```

**After analysis, enriched CONTEXT.md:**
```markdown
# CONTEXT.md

## Overview
Order management system handling the complete lifecycle from intake through fulfillment. Serves web app and fulfillment team.

## Core Domains
- Order — customer requests
- Inventory — stock management
- Fulfillment — shipping and delivery

## Glossary
- **Order** — customer request for goods. States: pending → confirmed → fulfilled → delivered.
  - Implementation: `src/models/Order.ts`, `src/modules/order/`

- **Fulfillment** — picking, packing, and shipping process.
  - Implementation: `src/modules/fulfillment/`

- **SKU** — product variant identifier (product + attributes).
  - Implementation: `src/models/Inventory.ts`

- **Allocation** — reserving inventory for an order.
  - Implementation: `src/modules/inventory/service.ts`

## Architecture
- **Layers**: API (controllers) → Service (business logic) → Data (repositories)
- **Patterns**: Repository pattern, Adapter pattern, Dependency injection, State machine
- **Integration**: Stripe (payments), FedEx (shipping), PostgreSQL (data)

## Related Documentation
- Architecture report: `docs/architecture-overview-2026-05-28.md`
- Architecture decision records: `docs/adr/`
```

## Output

After creating or updating CONTEXT.md:

1. **Print the path** — `CONTEXT.md created at /path/to/CONTEXT.md`
2. **In the report** — reference it: "See CONTEXT.md for the authoritative glossary and architectural decisions"
3. **Note in the summary** — "Domain glossary extracted and saved to CONTEXT.md"

## Key Principles

- **Lazy creation** — only create CONTEXT.md if it doesn't exist and you've found enough vocabulary
- **Vocabulary is grounded** — every term should reference actual code
- **Respect existing docs** — if CONTEXT.md exists, treat it as the source of truth for terminology
- **One level deep** — don't try to document every implementation detail; link to code instead
- **Terminology consistency** — once CONTEXT.md defines a term, use it everywhere in the report
